04 How to talk about the Order Diagnosis Agent

This is your strongest card — it maps almost line-for-line to the required qualifications. Two framing rules:

Frame it honestly, up front

It's a portfolio project modeling real enterprise complexity you saw at Bell — the four "backend systems" (CRM, billing, provisioning, network inventory) are mock services with synthetic data, not real telecom infrastructure. What's real: production-grade engineering practices — auth, rate limiting, structured observability, and an evaluation harness that found and fixed a genuine reliability bug. Say this plainly if asked "is this in production" — it reads as rigor, not a weakness, and gets ahead of the follow-up question.

Translate the architecture into their domain, unprompted

Supervisor + specialist sub-agents over CRM/billing/network maps directly onto a supervisor + specialist agents over income-doc extraction / policy-rule interpretation / risk calculation. Say that mapping out loud — it shows you're not just describing a past project, you're already thinking in their architecture.

05 Four stories, loaded and ready

The eval harness that caught a false-confidence bug — your anchor story

Situation
Built a 21-scenario evaluation harness (LLM-as-judge, precision/recall, false-confidence rate) for the multi-agent diagnosis system.
Task
Verify the agent wasn't just accurate on easy cases, but knew when it didn't know.
Action
Ran it against real model calls, not mocks. It surfaced a genuine bug: an unrecognized error code was being confidently misdiagnosed instead of flagged as insufficient evidence. Traced it to the tool/prompt design and fixed the abstain logic.
Result
Insufficient-evidence recall went from 0% to 100% — a silent failure mode became a measured, fixed guarantee. This is exactly the "know when not to trust the model" property a lending decision needs.

Production RAG at Bell Canada

Situation
Needed context-aware assistants over provisioning/assurance data serving live operations.
Task
Deliver a RAG pipeline accurate and reliable enough to run in production, not a demo.
Action
Designed the pipeline with LangChain/GPT-4 and vector DBs (Pinecone, ChromaDB); deployed containerized inference on AWS (Bedrock/Lambda/ECS) with Docker, Kubernetes, and GitHub Actions CI/CD; built structured logging and monitoring.
Result
92% retrieval accuracy in production, plus observability that sped up incident triage.

Translating ambiguous requirements into shipped software

Situation
At Team SI, led delivery across 3 concurrent client projects (healthcare, agricultural equipment) with different stakeholders and unclear scope.
Task
Own estimation, sprint planning, and direct client communication simultaneously across all three.
Action
Built a reusable React/Vue component library shared across projects to cut translation-to-code time; ran CI/CD automation on Azure DevOps.
Result
Release cycle went from multi-day manual deploys to same-day automated releases, across all three engagements.

Lending-domain systems, before AI was the job

Situation
At Berkadia, partners tracked loans across a fragmented multi-system workflow.
Task
Build a single-pane-of-glass view from origination through current status.
Action
Designed REST APIs, an Entity Framework data layer, and 20+ SQL Server stored procedures for real-time financial data access, plus Azure Queue-based async processing to decouple ingestion from display.
Result
Partners got one reliable view instead of five disconnected systems — direct, if pre-AI, exposure to lending data models and the reliability bar financial data demands.

07 Questions for the hiring manager

  • On the "AI Factory": What does the shared services layer actually provide today — model access, eval tooling, deployment, or all three?
  • On the deterministic/probabilistic split: What's the current balance between rule-based logic and LLM judgment in a live underwriting workflow?
  • On UAT & sign-off: How is a change to a policy prompt or agent validated before production — who reviews it, and what does UAT look like here?
  • On confidence: How is model uncertainty currently surfaced to underwriters — a score, a flag, a human-review queue?
  • On the team: How does the Residential Underwriting Product Squad work with QA, security, and compliance day to day?
  • On success: What does success in this role look like at the 6-month mark?

08 The two gaps — name them before they're asked

Platform: Azure / Databricks vs. AWS

Your production GenAI experience is AWS-centric (Bedrock, Lambda, ECS); the posting prefers Azure OpenAI Service, Databricks, and MLflow.

Say: "My hands-on hosting has been AWS, but the prompt engineering, retrieval design, and eval work are platform-agnostic — and I've already run CI/CD on Azure DevOps at a prior role. I'd expect to be productive on Azure/Databricks within the first few weeks."

Domain: telecom vs. regulated mortgage lending

Most of your AI work is telecom (Bell); the regulated-lending experience (Berkadia) predates the AI-engineer part of your career.

Say: lead with the domain-transferable instinct — evidence-cited outputs, structured audit logging, abstain-instead-of-guess — then mention Berkadia's lending data model as prior direct exposure to the domain, not as your main pitch.
